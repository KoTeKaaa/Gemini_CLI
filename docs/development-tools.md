# Инструменты разработки

`python_symbols` строит ограниченную карту Python с путями и строками.
Чтение требует подтверждения; синтаксические импорты не доказывают полноту зависимостей.
Без language server доступны карта проекта, `find_files` и `search_text`.

## Python language server

Опциональный [python-lsp-server 1.15.0](https://pypi.org/project/python-lsp-server/)
под MIT поддерживает Python 3.9+, Linux и Windows. Клиенту нужен Python 3.10+.
Jedi предоставляет definitions/references; extras Rope и Pyflakes — rename и диагностику.
Установите отдельно от приложения, без общего обновления его зависимостей:

```sh
python -m venv /opt/example/pylsp
/opt/example/pylsp/bin/python -m pip install -r client/requirements-lsp.txt
/opt/example/pylsp/bin/pylsp --help
```

В PowerShell:

```powershell
py -3.12 -m venv C:\Tools\pylsp
C:\Tools\pylsp\Scripts\python.exe -m pip install -r client/requirements-lsp.txt
C:\Tools\pylsp\Scripts\pylsp.exe --help
```

LSP работает локально через stdio; приложение не устанавливает и не запускает
конфигурации из workspace автоматически. Отдельный процесс может читать проект
и его конфигурацию: используйте только доверенный workspace. Буферы вывода ограничены,
запросы имеют ID, таймаут, отмену и shutdown. Сетевой LSP не поддерживается.

Укажите внешний сервер явно: `export GEMINI_CLI_PYLSP=/opt/example/pylsp/bin/pylsp`
или `$env:GEMINI_CLI_PYLSP='C:\Tools\pylsp\Scripts\pylsp.exe'`.
Попросите модель вызвать `python_lsp` с `action=definition` или `references`,
`filepath=src/app.py`, `line=10`, `character=4`. Строки с единицы, колонки UTF-16 с нуля.
Работа идёт по сохранённым файлам, максимум 200 Python-файлов / 4 МиБ;
несохранённый редакторный буфер не учитывается. При передаче `expected_sha256`
несовпадение версии запрещает запрос. Внешние URI и файлы без снимка отбрасываются;
результат помечен LSP, обычный текстовый поиск не считается точными ссылками.

`python_lsp action=diagnostics` ждёт publishDiagnostics именно выбранного документа.
Отсутствие ответа — таймаут, а не отсутствие ошибок. Некоторые серверы не передают
версию: тогда она показана как неизвестная, а снимок диска проверяется отдельно.
`action=rename new_name=новое_имя` преобразует текстовый WorkspaceEdit в обычный
набор правок: просмотр содержимого и diff, повторная проверка снимков, подтверждение,
запись через существующий журнал и `/undo`. Операции create/delete/rename файлов,
аннотации, пересечения edits и неизвестные версии отклоняются. Набор файлов
не является одной транзакцией: частичный результат отражается явно.

## Тесты

Попросите вызвать `run_tests modules=["tests.test_example"] timeout=120`.
Пустой список запускает discovery `tests/`. Запуск исполняет код проекта и требует
подтверждения. Результат содержит завершение процесса, exit code, число тестов,
failures/errors/skipped, ошибки discovery и ограниченные логи. Итоговый отчёт
передаётся отдельно от stdout; напечатанное тестом «успешно» не означает PASS.
Пустой набор, отмена, таймаут или отсутствующий отчёт не считаются успехом.
Отчёт временный; постоянных артефактов инструмент не создаёт (`artifacts=[]`).
В собранном CLI задайте абсолютный `GEMINI_CLI_PYTHON` на Python окружения проекта;
при запуске исходников по умолчанию используется текущий Python.

`affected_tests files=["pkg/core.py"]` предлагает модули unittest для явно
выбранных изменённых путей. Основа — прямые/транзитивные импорты, включая
относительные. Это рекомендация, а не обещание покрытия: конфигурация,
удалённые файлы, динамические импорты и неизвестные зависимости требуют полной
регрессии. Инструмент ничего не запускает и не скрывает неопределённость.

## Git

`git_read` принимает `action=status|diff|log|blame` и явный список `files`.
Для staged diff задайте `staged=true`; для blame — один файл и до 100 строк.
При переименовании выбирайте старый и новый путь. Вывод ограничен 32 КиБ,
усечение обозначено отдельно. Чтение не меняет ветку/index; внешний diff отключён.
Workspace должен быть корнем репозитория; пути с секретами и ссылки запрещены.

`git_commit action=prepare files=["src/app.py"] message="Fix parser" task="..."`
возвращает одноразовый token и полный выбранный diff, включая новые файлы.
`action=commit token=...` повторно показывает план и требует подтверждения.
Выбираются целые файлы, включая их текущие staged и unstaged изменения;
hunks отдельно не выбираются. HEAD, index и файлы проверяются до запуска.
Посторонние staged/unstaged правки сохраняются: коммит использует временный index,
а реальный index блокируется и обновляется только для выбранных путей.
Hooks выполняются обычно; их ошибки/вывод не скрываются. Инструмент не делает push.
При остановке hook или Sphinx завершите проверку в предоставленном им интерфейсе;
не запускайте повторный коммит, пока исходный процесс работает.

## Pull request через GitHub MCP

Настройте персональное подключение по [гайду GitHub](mcp-github.md).
В приватном `mcp.json` явно выберите `list_pull_requests`, `create_pull_request`,
`update_pull_request`, `pull_request_read`. Для создания/обновления нужны права
**Pull requests: Read and write** только выбранного репозитория; для checks —
**Checks: Read**, для статуса — **Commit statuses: Read**. Contents write не нужен:
инструмент не делает push. GitHub MCP должен разрешать запись; read-only endpoint
для создания PR не подходит. Права и стоимость проверяйте у GitHub.

После `/mcp login github memory` и `/mcp enable github` явно попросите создать PR:
`github_pr action=create base=dev title="Fix parser" body="Что исправлено и чем проверено"`.
Ветка должна быть опубликована отдельно по вашей команде; origin — репозиторий
на github.com. Перед каждым MCP-вызовом проверяйте показанные аргументы.
Создаётся draft PR; повторное create возвращает уже открытый PR той же ветки/base.
`action=update` меняет title/body, `action=checks` возвращает checks и combined status.
Неизвестные/неполные checks не означают PASS. Ошибка 401/403, неполный список,
неизвестный ответ или сетевой сбой не запускают скрытый повтор записи.
Если публикация оборвалась, сначала проверьте удалённый PR.
Автоматических push, merge и расширения прав нет.
