# Миграция подписок

Сначала примените миграции `supabase/migrations` в отдельном preview-проекте.
Проверьте `supabase/tests/account_subscriptions.sql` через SQL Editor или psql
с административным соединением: сценарий двух пользователей откатывает fixtures.
Тест использует зарезервированные UUID; запускайте только в изолированной БД.

Существующие auth/chats/messages не изменяются. Автоматического доступа всем
старым аккаунтам нет. До включения проверки допуска владелец должен явно создать
подписку каждому нужному `auth.users.id`, указать срок, модели, возможности,
бюджет/окно и параллельность. При отсутствии подписки рабочий API будет закрыт.
Сначала сверить user_id; email и редактируемые metadata не определяют права.

`service_role` управляет новыми таблицами только на сервере. Пользователь читает
лишь свою подписку и не меняет права. Неактивированная подписка может иметь
пустой user_id; приглашения закрыты от пользовательского REST-доступа.
В схеме подписок нет флага администратора: приглашение никогда его не выдаёт.
Версия прав увеличивается триггером при каждом изменении.

Откат S0.1: сначала экспортировать новые таблицы и остановить использующий их
preview-сервис, затем выполнить `deploy/rollback_account_subscriptions.sql`.
Это удаляет только новые таблицы/триггер и функцию; auth и история сохраняются.
После следующих миграций откатывать их в обратном порядке; CASCADE намеренно нет.
Не применять миграцию или откат к рабочей базе без отдельной задачи поставки.

Следующая миграция добавляет `subscription_requests` и RPC резерва бюджета.
Вызов доступен только серверному `service_role`; задайте его ключ в приватном
серверном окружении `SUPABASE_SERVICE_ROLE_KEY`. Клиентский токен его не заменяет.
Каждый вызов Gemini и Tavily, включая продолжения, получает отдельный request_id.
Повтор того же ID отклоняется, расход не возвращается после таймаута/рестарта.
Окна фиксируются по UTC epoch; записи старых окон остаются для дедупликации.
Это бюджет подписки, а не сведения о квоте провайдера.

В preview Supabase Auth отключите **Allow new users to sign up** и **Allow anonymous
sign-ins**. Серверный `/auth/signup` всегда отвечает 403. Владелец приглашает
аккаунт через `/admin/api/accounts/invite`; это письмо регистрации, а не подписка.
Разрешите redirect URL `https://<panel-origin>/account/confirm` в Auth URL Configuration.
Обычный пользователь, даже имея валидный Supabase-токен, без подписки не получает API.
Проверка этих настроек preview обязательна; настройки рабочего проекта не менять
как побочный эффект локальной разработки.
Откат этой миграции перед S0.1: удалить RPC `reserve_subscription_request(uuid,
uuid, text, text, text[])`, затем таблицу `subscription_requests` после экспорта.
