# Миграция истории чатов

[Русский](history-migration.md) · [English](en/history-migration.md)


История хранит устойчивые идентификаторы событий и границы ходов, чтобы продолжение,
сжатие и ветвление чатов не нарушали порядок сообщений. SQL в `deploy/history_events.sql`,
`history_append.sql` и `history_boundaries.sql` применяется в этом порядке.
Автодеплой не запускает SQL. Перед обновлением существующей базы сверьте её схему
и историю миграций; уже применённые изменения повторять не нужно.

## Договор

`messages.id` — постоянный UUID события. `turn_id` объединяет пользовательский ход,
`request_id` — отдельную генерацию/продолжение, `event_index` — неотрицательный порядок
сохраняемых событий внутри запроса. Уникальность `(chat_id,request_id,event_index)`
предотвращает повторную запись идентифицированного события. Старые вставки без этих
полей продолжают работать: идентичность и порядок выдаёт БД, статус — `legacy`.
Статусы новых событий: `running`, `completed`, `cancelled`, `failed`.
`call_id` и `thought_signature` сохраняют идентичность и подпись вызова инструмента.
Это не журнал сырых аргументов: существующая фильтрация постоянной истории обязательна.

`sequence` — глобальный монотонный номер записи; внутри чата читать по нему.
Прежние строки получают последовательность по `(created_at,id)` под блокировкой
таблицы. При одинаковом `created_at` исходный причинный порядок неизвестен;
сортировка по UUID обеспечивает воспроизводимость, а не восстановление причинности.
Не присваивать старой истории выдуманный статус завершения или границы ходов.
Номер последовательности может содержать пропуски после отката транзакции.

`chats.summary` и `summary_boundary` задаются вместе; граница обязана принадлежать
этому же чату. `fork_parent_id` ограничен чатом того же владельца, `fork_boundary`
при существующем родителе — его сообщением. PostgreSQL 17 поддерживает выборочное
`ON DELETE SET NULL`; удаление источника сохраняет fork и его владельца, очищая
ссылку на родителя. После удаления источника boundary может остаться как неразрешимый
идентификатор происхождения либо стать NULL при каскадном удалении сообщения;
восстанавливать источник по нему нельзя. Завершённость целого хода и безопасность
summary проверяются RPC; одной ссылочной целостности недостаточно.

## Права и порядок поставки

Миграция оставляет authenticated-политики владения chats/messages и Supabase Auth.
Она удаляет две прежние разрешающие anon-политики messages и отзывает публичные/anon
права на messages. Старый клиент со входом по JWT работает; анонимная история закрывается.
Service-role остаётся серверным секретом и не нужен в клиенте.

Сначала применить SQL в изолированной preview-БД с исходными chats/messages и
политиками. Таблицы подписок не заменяют этот отсутствующий в репозитории baseline.
Нужны административное SQL-соединение и PostgreSQL 17. Перед production сделать
резервную копию и оценить размер messages: backfill удерживает блокировку таблицы.
Проверить миграцию на пустой БД и на старых строках, включая одинаковые timestamps.
Затем выполнить `supabase/tests/history_events.sql` административным соединением:
fixtures двух auth.users откатываются; сценарий проверяет старую вставку, уникальность,
RLS двух владельцев/anon, границы summary, владение fork и удаление источника.
Зарезервированные UUID предназначены только для отдельной тестовой БД.

Схему применять до runtime, использующего новые колонки. `deploy/promote.py` и CI
не применяют SQL. Сбой миграции откатывается целиком; после успешной миграции прежний
runtime остаётся совместимым. Автоматический обратный DROP новых колонок запрещён:
это уничтожило бы сохранённые идентификаторы, summary и происхождение fork.

## Запись событий

После схемы применяется `deploy/history_append.sql`. Оба RPC — `SECURITY INVOKER`,
с пустым search_path, только для authenticated и с явной проверкой auth.uid владельца.
`append_history_events(target_chat,events)` принимает до 100 уже отфильтрованных
событий и возвращает число новых строк. Весь batch атомарен; блокировка чата
сериализует конкурирующие вызовы адаптера. Повтор по id или request_id/event_index
с теми же данными ничего не добавляет; изменённый повтор вызывает ошибку и откат.
Повтор исходного running-события после финализации — no-op при точном совпадении
всех остальных полей: терминальное состояние сохраняется без записи.
Один заданный id, указывающий не на ту же строку, что request ordinal, также запрещён.
Если есть request_id/event_index, нужны оба и turn_id. Старый формат без них разрешён.
Функция не выполняет redaction самостоятельно: её делает сервер до RPC.

`update_history_request_status(target_chat,request_uuid,new_status)` меняет только
running-события этого запроса на completed/cancelled/failed, возвращает число изменений.
Повторная финализация не переписывает терминальные/legacy строки. При отсутствии
событий функция возвращает 0, отдельный tombstone запроса не создаётся. Генерацию
и отсечение поздних событий по-прежнему защищают бюджет/отмена runtime; UUID запроса
резервируется сервером до записи/вызова провайдера. Этот RPC не обещает exactly-once
для внешних инструментов или провайдера.

Изолированный runner применяет сначала history_events.sql, затем остальные
deploy/history_*.sql по имени и выполняет все history_*.sql fixtures кроме baseline.

## Границы summary и fork

`set_history_summary(target_chat,summary_text,boundary_id)` возвращает true. Требует
сводку до 8192 символов, целый completed-ход с начальным user и конечным непустым
model, согласованные пары name/call_id, отсутствие поздних событий этого хода.
Граница находится до последнего user и не двигается назад. Сводка заменяется атомарно,
сообщения сохраняются. Python runtime создаёт сводку только из отфильтрованного контекста.

`fork_history_chat(target_chat,new_title,boundary_id)` возвращает JSON объекта chats.
NULL boundary выбирает последнюю безопасную границу. Копируется полный префикс
до неё с новыми UUID событий, исходными turn/request/tool IDs, signatures и порядком.
Сводка копируется лишь при включении её границы в префикс, с новым boundary UUID.
Копия повторно очищается консервативно: все tool outputs и содержимое именованных
model calls заменяются redacted, arguments содержат только допустимые path/line поля.
Обычные user/model сообщения сохраняются. Исходный чат остаётся неизменным.
Ранние прерванные ходы префикса сохраняются; runtime восстанавливает недостающие
результаты только как interrupted, без автоматического повторения действий.
Создание чата, копирование и summary выполняются одной транзакцией; ошибки не
оставляют видимый частичный fork. Все функции invoker-scoped и закрыты для anon.
