# История S4: совместимая схема

S4.1 подготавливает схему; запись событий, RPC, fork и compact ещё не реализованы.
SQL подготовлен в `deploy/history_events.sql`. Это проект миграции, а не
автоматически применяемый deploy-скрипт. Supabase CLI в текущем окружении отсутствует.
При доступном CLI создать канонический файл через `supabase migration new history_events`
и перенести туда SQL; не применять и проект, и каноническую миграцию повторно.

## Договор

`messages.id` — постоянный UUID события. `turn_id` объединяет пользовательский ход,
`request_id` — отдельную генерацию/продолжение, `event_index` — неотрицательный порядок
сохраняемых событий внутри запроса. Уникальность `(chat_id,request_id,event_index)`
предотвращает повторную запись идентифицированного события. Старые вставки без этих
полей продолжают работать: идентичность и порядок выдаёт БД, статус — `legacy`.
Статусы новых событий: `running`, `completed`, `cancelled`, `failed`.
`call_id` и `thought_signature` сохраняют идентичность и подпись вызова инструмента.
Это не журнал сырых аргументов: существующая фильтрация постоянной истории обязательна.

`sequence` — глобальный монотонный номер записи; внутри чата читать по нему.
Прежние строки получают последовательность по `(created_at,id)` под блокировкой
таблицы. При одинаковом `created_at` исходный причинный порядок неизвестен;
сортировка по UUID обеспечивает воспроизводимость, а не восстановление причинности.
Не присваивать старой истории выдуманный статус завершения или границы ходов.
Номер последовательности может содержать пропуски после отката транзакции.

`chats.summary` и `summary_boundary` задаются вместе; граница обязана принадлежать
этому же чату. `fork_parent_id` ограничен чатом того же владельца, `fork_boundary`
при существующем родителе — его сообщением. PostgreSQL 17 поддерживает выборочное
`ON DELETE SET NULL`; удаление источника сохраняет fork и его владельца, очищая
ссылку на родителя. После удаления источника boundary может остаться как неразрешимый
идентификатор происхождения либо стать NULL при каскадном удалении сообщения;
восстанавливать источник по нему нельзя. Завершённость целого хода и безопасность
summary будут проверяться будущим RPC, одной ссылочной целостности недостаточно.

## Права и порядок поставки

Миграция оставляет authenticated-политики владения chats/messages и Supabase Auth.
Она удаляет две прежние разрешающие anon-политики messages и отзывает публичные/anon
права на messages. Старый клиент со входом по JWT работает; анонимная история закрывается.
Service-role остаётся серверным секретом и не нужен в клиенте.

Сначала применить SQL в изолированной preview-БД с исходными chats/messages и
политиками. Таблицы подписок не заменяют этот отсутствующий в репозитории baseline.
Нужны административное SQL-соединение и PostgreSQL 17. Перед production сделать
резервную копию и оценить размер messages: backfill удерживает блокировку таблицы.
Проверить миграцию на пустой БД и на старых строках, включая одинаковые timestamps.
Затем выполнить `supabase/tests/history_events.sql` административным соединением:
fixtures двух auth.users откатываются; сценарий проверяет старую вставку, уникальность,
RLS двух владельцев/anon, границы summary, владение fork и удаление источника.
Зарезервированные UUID предназначены только для отдельной тестовой БД.

Схему применять до runtime, использующего новые колонки. `deploy/promote.py` и CI
не применяют SQL. Сбой миграции откатывается целиком; после успешной миграции прежний
runtime остаётся совместимым. Автоматический обратный DROP новых колонок запрещён:
это уничтожило бы сохранённые идентификаторы, summary и происхождение fork.

Изолированная проверка: `bash supabase/tests/verify_history_schema.sh` — PASS на
PostgreSQL 17 через rootless Podman для пустой БД и старых строк. Проверены порядок,
legacy insert, уникальность, authenticated/anon RLS, summary/fork и удаление источника.
Контейнеры и их volumes удалены; live DDL не применялся. RPC ещё не добавлены.
Синтаксис выборочного SET NULL подтверждён [документацией PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-constraints.html).
