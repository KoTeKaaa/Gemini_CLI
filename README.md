# Gemini_CLI

`Gemini_CLI` — это консольный клиент для работы с Gemini через локальный/удалённый FastAPI-сервер.
Проект поддерживает авторизацию через Supabase, выбор чатов, создание новых комнат диалога и потоковую выдачу ответа модели прямо в терминал.

## Возможности

- Авторизация по email и паролю
- Создание и выбор постоянных чатов
- Временный режим без сохранения истории в БД
- Потоковый вывод ответа модели в консоль
- Чтение и запись файлов и выполнение команд после подтверждения пользователя
- Несколько вызовов инструментов в одном ответе с сохранением контекста диалога
- Автоматическое обновление истёкшей сессии и сообщения об ошибках сохранения
- Переключение модели командой `/model`
- Переключение чата командой `/chat`
- Сохранение сессии пользователя в `~/.gemini_cli`
- HTTPS для удалённого API и изоляция чатов разных пользователей
- Сборка исполняемого файла через PyInstaller

## Структура проекта

- `main.py` — CLI-клиент
- `server.py` — FastAPI-сервер, который обрабатывает авторизацию, чаты и запросы к Gemini
- `client/` — зависимости, запуск и сборка клиента на Linux
- `deploy/` — установщик и конфигурация сервера для Ubuntu/Debian
- `tests/` — тесты клиента, сервера и предварительных проверок установщика

## Требования

- Python 3.10+

  - `requests`
  - `prompt_toolkit`

  - `pydantic`

## Настройка сервера

Перед запуском `server.py` нужно создать файл `.env` в корне проекта и указать переменные:

```env
API_KEY=your_gemini_api_key
SUPABASE_URL=your_supabase_url
SUPABASE_ANON_KEY=your_supabase_anon_key
```

## Установка

Рекомендуется запускать проект в виртуальном окружении:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install requests prompt_toolkit rich fastapi uvicorn google-genai python-dotenv supabase pydantic
```

## Запуск

### 1. Запустить сервер локально

```powershell
python server.py
```

Этот способ слушает `0.0.0.0:8000` без TLS. Для VPS используйте скрипт ниже.

### Автоматическая установка на VPS (Ubuntu/Debian)

Создайте **вне репозитория** файл с
`API_KEY`, `SUPABASE_URL` и `SUPABASE_ANON_KEY` в формате `KEY=value`.
На сервере из каталога проекта запустите:

```bash
sudo ./deploy/install.sh --host SERVER_IP --env-file /absolute/path/server.env
```

Скрипт спросит, существует ли сертификат. При ответе «да» передайте пути к
имеющимся файлам (или сразу укажите их в команде):

```bash
sudo ./deploy/install.sh --host SERVER_IP --cert-mode existing \
  --cert-file /absolute/path/fullchain.pem --key-file /absolute/path/privkey.pem \
  --env-file /absolute/path/server.env
```

При ответе «нет» скрипт выпустит бесплатный сертификат Let's Encrypt для
публичного IP или DNS-имени через acme.sh и настроит его продление. Для выпуска
и продления **публичный TCP-порт 80 должен быть открыт и свободен**. Порт 443
не требуется. Для запуска без вопросов используйте `--cert-mode issue`.
Не используйте этот режим, если порт 80 занят другим сервисом; укажите
существующий сертификат. Перед установкой можно проверить существующий
сертификат командой `sudo ./deploy/install.sh --check` с теми же параметрами.
acme.sh устанавливается отдельно для этого сервиса и не меняет сертификаты 3x-ui.

Порт HTTPS по умолчанию — `9443`; другой задаётся через `--port`. Скрипт проверяет
совпадение сертификата с адресом, при отсутствии Python устанавливает его,
создаёт `/opt/gemini-cli/.venv` и устанавливает серверные зависимости. Затем
он копирует **только три** необходимые переменные в `/etc/gemini-cli/server.env`
с правами `0600`,
запускает API на `127.0.0.1:8000`, Nginx на выбранном HTTPS-порту и включает
автозапуск. Таймер перечитывает обновлённый сертификат каждый час. Для
существующего сертификата его продление должно быть настроено отдельно; для
выпущенного скриптом это делает acme.sh через cron. После установки
проверьте доступность HTTPS-порта с другого устройства и откройте его в сетевых
правилах хостинга, если требуется.

### 2. Запустить CLI-клиент

На Linux из каталога проекта:

```bash
./client/run.sh
```

При первом запуске скрипт проверяет Python 3.10+, создаёт `.venv`, устанавливает
только клиентские зависимости и запускает `main.py` через Python. Для одной
только установки окружения используйте `./client/run.sh --setup-only`. Если
Python установлен под другим именем, задайте `PYTHON=/путь/к/python3`.

На Windows установите клиентские зависимости из `client/requirements.txt` и
запустите `python main.py`:

```powershell
python -m pip install -r client/requirements.txt
python main.py
```

При первом запуске клиент попросит указать адрес сервера, например:

```text
https://SERVER_IP:9443
```

Сертификат должен соответствовать указанному IP или DNS-имени. Прямое подключение по HTTPS
к `server.py:8000` не работает; для удалённого сервера нужен HTTPS.
HTTP разрешён только для `localhost` и loopback-адресов, например `http://127.0.0.1:8000`.
Если адрес введён без протокола, приложение выбирает HTTPS для удалённого адреса и HTTP для локального.

## Как пользоваться

После запуска вы увидите меню выбора:

- временный чат
- создание нового чата
- список сохранённых чатов

Внутри чата доступны команды:

- `/model` — сменить модель
- `/chat` — переключиться на другой чат
- `exit`, `quit`, `q`, `выход` — завершить работу

Если модель запрашивает доступ к файлам или выполнение команды, клиент показывает
запрос и спрашивает подтверждение. Доступ к файлам ограничен текущей рабочей
папкой; переход наружу через `..` или символическую ссылку блокируется.
Известные файлы с секретами клиент не читает. Запись выполняется через
временный файл и замену после успешной записи; результат показывается для
каждого файла. Команда `/cd` меняет рабочую папку, в том числе по
относительному пути. При отмене меню `/chat` текущий чат сохраняется.

## Поддерживаемые модели

По умолчанию используется `gemini-3.5-flash-lite`. Через `/model` можно выбрать:

| Модель | Идентификатор API |
| --- | --- |
| Gemini 3.5 Flash-Lite | `gemini-3.5-flash-lite` |
| Gemini 3.8 Flash | `gemini-3.8-flash` |
| Gemini 3.7 Flash | `gemini-3.7-flash` |
| Gemini 3.6 Flash | `gemini-3.6-flash` |
| Gemini 3.5 Flash | `gemini-3.5-flash` |

Это стабильные модели для текстового ответа и вызова функций из
[списка Gemini API](https://ai.google.dev/gemini-api/docs/models). Доступность и
лимиты зависят от ключа API и отображаются в Google AI Studio. Клиент передаёт
выбранный идентификатор серверу, а сервер вызывает
`client.models.generate_content_stream` из Google Gen AI SDK. Для продолжения
после вызова инструмента Gemini 3 клиент возвращает выданную моделью
`thought_signature` вместе с вызовом.

## Готовый файл для Linux и сборка

Для Linux выполните из каталога проекта:

```bash
./client/build.sh
./dist/gemini-cli
```

Скрипт устанавливает PyInstaller и создаёт один исполняемый файл
`dist/gemini-cli`. В нём уже находятся Python и клиентские зависимости;
`server.py` и серверные ключи туда не входят. Файл собран для архитектуры
и системных библиотек компьютера сборки; для другой Linux-системы соберите
его там же или на совместимой системе. Адрес сервера и сессия хранятся в
домашней папке пользователя, как при запуске через Python.
Для GitHub Release приложите `dist/gemini-cli` как файл релиза и укажите
целевую архитектуру и дистрибутив сборки. Каталоги `dist/`, `build/` и `.venv/`
не добавляются в Git.

Для Windows `.exe` собирается на Windows через PowerShell:

```powershell
./client/build.ps1
```

Скрипт создаёт отдельное окружение `.venv-win`, устанавливает клиентские
зависимости и PyInstaller. После сборки файл находится в `dist\gemini-cli.exe`.
Если Windows-компьютера нет, после push в ветку `dev` workflow
`Build Windows client` соберёт `.exe` на GitHub Actions. Скачайте артефакт
`gemini-cli-windows-x64` из завершённого запуска и приложите `.exe` к GitHub
Release. Сборка на Windows должна завершиться успешно до публикации файла.

## Хранение данных

Клиент сохраняет:

- токен сессии — в `~/.gemini_cli/session.json`
- адрес сервера — в `~/.gemini_cli/server_config.json`

На POSIX-системах каталог и файл сессии доступны только владельцу. Истёкшая
сессия обновляется по refresh token; если обновление невозможно, клиент
предлагает войти снова. Лог вызовов инструментов не содержит их аргументы.

## Примечания

- Для постоянных чатов сервер использует Supabase таблицы `chats` и `messages`.
- Для удаления чата вместе с сообщениями в БД необходим внешний ключ
  `messages.chat_id` с `ON DELETE CASCADE`. Сервер проверяет владельца чата
  перед чтением истории и удалением; RLS в Supabase также должна быть настроена.
- Результаты чтения локальных файлов не сохраняются в истории постоянного чата
  в открытом виде.
- При ошибке `429` сервер сообщает, что у модели закончились бесплатные токены или лимит запросов, и предлагает сменить модель.

## Проверки

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m unittest discover -s tests -p 'test_*.py' -q
bash tests/test_deploy_install.sh
```

Тест предварительной проверки установщика не заменяет запуск на реальном VPS.
Интеграционный тест с настоящим Supabase запускается отдельно при
`RUN_SUPABASE_INTEGRATION=1` и заданных учётных данных двух тестовых пользователей.
